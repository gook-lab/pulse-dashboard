## ① 실거래 API — 응답 필드

`RTMSDataSvcAptRent`(전월세) 실제 응답 1건:

```json
{
  "aptNm": "래미안블레스티지",  "aptSeq": "11680-4800",  "buildYear": 2019,
  "dealYear": 2026, "dealMonth": 4, "dealDay": 8,
  "deposit": "5,000", "monthlyRent": 560, "excluUseAr": 84.943, "floor": 14,
  "umdNm": "수서동", "jibun": 1280, "roadnm": "선릉로 8",
  "sggCd": 11680, "roadnmcd": 4166071, "roadnmbonbun": "00008", "roadnmbubun": "00000",
  "contractTerm": " ", "contractType": " ", "preDeposit": " ", "preMonthlyRent": " ", "useRRRight": " "
}
```

설계가 필요로 한 필드 **전부 존재**: 단지명 · 전용면적 · 금액 · 층 · 법정동. **STOP 조건 해당 없음.**

**보너스로 더 있는 것**: `aptSeq`(단지 고유 ID), `buildYear`(준공연도), `roadnm`+`umdNm`+`jibun`(주소 → 지오코딩 입력).
**없는 것**: 세대수, 동수, 좌표.

## ② `aptSeq` 안정성 — 강남구 전월세 3개월 전수(5,343건)

```
distinct aptSeq        475
distinct aptNm         463
aptSeq 누락              0 건
한 aptSeq → 여러 이름     0 건   ← 완전 일관
한 이름 → 여러 aptSeq    10 건   ← 문자열 매칭이 위험한 이유
```

이름이 겹치는 실제 사례:

```
"삼성"          → 11680-330, 11680-316, 11680-302   (서로 다른 3개 단지)
"동부센트레빌"   → 11680-392, 11680-601, 11680-237   (서로 다른 3개 단지)
"신동아"        → 11680-319, 11680-47
"e-편한세상"    → 11680-3622, 11680-3592
"삼익"          → 11680-317, 11680-332
"대우디오빌"     → 11680-560, 11680-275
```

**설계대로 아파트명 문자열 매칭을 했다면 강남구 한 곳에서만 10건의 오매칭이 발생한다.** "삼성"이라는 이름의 서로 다른 3개 단지가 하나로 합쳐져 시계열이 섞이고, 없던 모멘텀이 생긴다. 그리고 이건 설계가 **critical gap 2 (오매칭에 사후 검출 수단이 없음)** 로 이미 걱정했던 바로 그 시나리오다.

`aptSeq`를 키로 쓰면 이 문제가 존재하지 않는다.

## ③ 페이지네이션 — 검증 완료

```
강남구 202601  page1 1000 · page2 1000 · page3 61   총 2,061
강남구 202604  page1 1000 · page2  441              총 1,441
강남구 202606  page1 1000 · page2  841              총 1,841
```

`numOfRows=1000` 초과가 **실제로 발생**. 9개 샘플 중 6개가 1000 초과. 최대 2,061.
→ `totalCount` 기반 `pageNo` 루프는 추정이 아니라 필수. 콜 수 배율 약 **1.7배**.

## ④ 소요시간 — 재추정 필요

```
1콜 평균 5,142ms · 최대 7,520ms   (설계 가정: 1,000ms 이하)
```

전월세만, 15개월, 페이지네이션 1.7배 기준:
```
25구 × 15개월 × 1.7 = 638콜
638 ÷ 동시성 5 × 5.1초 ≈ 651초 ≈ 11분
```
매매까지 포함하면 약 **22분**. 설계의 "30분 넘으면 12→6개월로 축소" 기준 안에는 들어오지만 여유가 없다.

## ⑤ 신고지연 — 측정 미완

전월세 월별 `totalCount` 추이:
```
강남구  6개월전 2,061 · 3개월전 1,441 · 1개월전 1,841
송파구  6개월전 2,052 · 3개월전 1,488 · 1개월전 1,282
중구    6개월전   438 · 3개월전   257 · 1개월전   247
```

**계절성과 섞여 신고지연만 분리되지 않는다.** 강남은 1개월 전이 3개월 전보다 오히려 많다. 202601(1월)이 높은 것은 이사철 전 계약 집중일 가능성이 크다.

또한 **전월세는 확정일자 기준이라 매매(계약 후 30일 신고 의무)보다 지연이 짧다.** 매매 데이터를 받지 못해 정작 검증이 필요한 쪽을 못 쟀다.

→ **설계 D11(기준월 = 3개월 전)은 그대로 유지한다.** 30일 신고 의무는 제도적 사실이고, 측정이 안 됐다고 해서 없어지지 않는다. 매매 API가 열린 뒤 같은 측정을 다시 한다.

## ⑥ 부가 API — 전부 실패

```
공동주택 단지목록 V3   HTTP 404  "API not found"
공동주택 단지목록 V2   HTTP 500  "Unexpected errors"
공동주택 기본정보 V3   HTTP 500  "Unexpected errors"
국토부 지오코더        HTTP 500  "Unexpected errors"
```

엔드포인트 경로 오류인지 미승인인지 이 결과만으론 구분되지 않는다. 다만 **실거래 응답만으로 세대수를 뺀 나머지가 다 나오므로 우선순위가 낮아졌다.**

| 필요했던 것 | 원래 출처 | 실거래 응답으로 대체 |
|---|---|---|
| 단지 고유 ID | `kaptCode` | **`aptSeq`** ✓ |
| 단지명 | `kaptName` | `aptNm` ✓ |
| 준공연도 | `kaptUsedate` | `buildYear` ✓ |
| 주소(지오코딩 입력) | `kaptAddr` | `roadnm` + `umdNm` + `jibun` ✓ |
| 세대수 | `kaptdaCnt` | **없음** — 거래건수로 대체 |

세대수는 "세대수 상위 300개 매칭률 90%" 게이트에 쓰려던 값인데, 매칭 자체가 사라졌으므로 그 게이트도 함께 사라진다.

## ⑦ 규모 — 3,000이 아니다

강남구 한 곳의 **3개월 전월세**에만 475개 단지가 등장했다. 12개월·매매 포함이면 더 늘고, 25개 구로 확장하면:

```
보수적 추정: 8,000 ~ 12,000 단지   (설계 문서의 "약 3,000"은 크게 과소추정)
```

영향:
- `apt-signals.json` ~3.4MB → **~14MB** (여전히 RSS 50MB 예산 안)
- `screen` 응답 ranked gzip 20KB → **~80KB** (여전히 문제 없음)
- 마스터 840KB → **~3.4MB** (ETag 캐시라 1회)
- **지도**: 12,000 마커는 서울 전역에서 절대 불가 → 디자인 리뷰 D3(줌 레벨별 동 단위 집계)가 선택이 아니라 필수가 됐다

## 시그널 품질 — 실데이터를 봐야만 드러난 문제 3연쇄

설계와 리뷰가 예측하지 못한 것들이 순서대로 나왔다. 전부 화면은 멀쩡히 돌면서 순위만 틀리는 종류다.

### ① 이상치 — momentum6 = +977%

```
삼익(금천 시흥동)   202509  전용114㎡  보증금  5,000만 → 평당  144만
강변현대(광진)      202510  전용130㎡  보증금 10,000만 → 평당  253만
삼환(영등포)        202510  전용 84㎡  보증금  5,000만 → 평당  195만
```

같은 단지 다른 달은 평당 1,100~2,800만. `monthlyRent=0` 이라 전세로 잡히지만 실제로는
갱신계약 증액분만 신고했거나 특수관계 거래로 보인다. 그 달에 거래가 그 1건뿐이면
중앙값이 곧 이상치가 되고, 6개월 전 기준점이 되면 +977% 가 나온다.

**대응**: 단지 내 평당가 중앙값 대비 `[0.4, 2.5]` 밖 제외. IQR 은 표본 3건짜리 단지를
죽이므로 쓰지 않았다. 제외율 **0.41%** (368,892건 중 1,506건) — 과잉 제거 아님.
→ 977% → 228%

**아웃사이드 보이스 #9 가 맞았고 "중앙값이 이미 방어한다"는 반박이 틀렸다.**
중앙값은 같은 달 안의 이상치는 막지만, 그 달에 이상 거래 1건뿐이면 중앙값이 곧 그 이상치다.

### ② 구성 변화(mix shift) — momentum6 = +228%

```
천왕이펜하우스2단지(구로 천왕동)  이상치 제외 0건인데 +228%
  202508  평당  679 × 13건      ← 저가 그룹만 거래된 달
  202602  평당 1370, 2257, 1370  ← 고가 그룹만 거래된 달
```

한 단지 안에 평당 679만 그룹과 1,984만 그룹이 공존한다. 둘 다 단지 중앙값 대비 0.5~1.45배라
이상치 컷을 통과하는데, 달마다 어느 그룹이 거래되느냐로 월 중앙값이 널뛴다.

**대응**: 시그널 계산에 **3개월 이동 중앙값**을 쓴다(차트에는 실제 월별 중앙값을 그대로 보여준다).
창 안의 원시 거래를 전부 모아 중앙값을 낸다 — 중앙값의 중앙값이 아니다.
→ 천왕이펜하우스2단지 227.94% → **101.7%**

**한계**: 중앙값은 평균이 아니므로 두 가격대가 완벽히 균형 교대하면 완화되지 않는다.
실데이터는 그렇게 규칙적이지 않아 잘 듣는다. 테스트에 한계 케이스를 명시해 뒀다.

### ③ 남은 고값은 정제 실패가 아니라 데이터의 실제 성질

평활 후 momentum6 상위:

```
서초포레스타2단지   서초  +298%  거래 187건
강일리버파크5단지   강동  +199%  거래  47건
상림마을7단지      은평  +234%  거래  19건   (12개월)
세곡리엔파크3단지   강남  +141%  거래  23건   (12개월)
```

전부 **공공임대·장기전세 단지**다(보금자리, 뉴타운, 공공임대). 임대 보증금과 일반 전세가
같은 `aptSeq` 아래 함께 신고되므로, 6개월 전엔 임대 위주 / 지금은 일반 전세 위주면
진짜로 200% 차이가 난다. 거래 187건이면 표본 부족도 아니다.

이건 자동 정제 대상이 아니다. 설계 D9(거래건수 노출로 사용자가 신뢰도 판단)와
D11(상세 모달 = 검증 순서)이 정확히 이 상황을 위해 있다. 화면이 시계열을 보여주고
사용자가 판단한다.
